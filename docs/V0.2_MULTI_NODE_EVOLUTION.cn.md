# v0.2 多节点进化

状态：已确认的目标架构，尚未成为已实现的运行时契约。

本文定义 v0.2 如何让同一个自成长 Agent 在本地开发机和远程运行节点之间持续进化。v0.2 保留 v0.1 的证据、harness 和节点本地安全模型，同时增加一条基于私有 Git 仓库的可复用 Agent 资产分发路径。

英文对应文档为 [`docs/V0.2_MULTI_NODE_EVOLUTION.md`](V0.2_MULTI_NODE_EVOLUTION.md)。

## 核心决策

v0.2 分成三个相互独立的平面：

1. Evi 原生控制面（`GoalRuntime`、`Harness`、canonical evidence、`OutcomeReceipt` 与
   有边界的 `Direction Proposal`）拥有本地方向、verification 和自进化 effect。
2. 私有 LuBan 仓库保存已接受、可复用的 Agent 资产及版本历史。
3. Evi 在各节点上负责评估、提案、选择、验证、激活、观察、修订和退役。

GitHub Issues 和 Projects 可以展示外部规划、状态或交付 evidence，但不是必需控制面。

LuBan 是 Agent 资产注册库和发布源，不是运行时编排器、安装守护进程、共享状态数据库或决策引擎。`skill-manager` 只作为同步、冲突、备份和恢复实现的参考，不是 v0.2 的依赖或标准。

## 核心运行时边界

v0.2 的进展不等于收集更多工具、skill 或学习到更多 procedure。它的核心目标是一个可持续的
Agent runtime：同一个主体在 session、进程重启和独立选择资产的节点上仍能保持身份，并让其工作可检查。必须具备的
core capability 是：

1. **Goal 连续性**：绑定意图、Decision Owner、checkpoint、验收和 `OutcomeReceipt`，使 Goal 能跨越
   session 或进程边界。
2. **Context 编译**：选择有边界、具权威性的 Goal、项目、运行时和 recall context；冲突或过期证据不得
   变成隐式的 transcript dump。
3. **由证据驱动的自监督**：记录 action/effect，区分 success、failure 和 outcome-unknown，并在不把模型
   置信度当作 verification 的前提下恢复或暂停。
4. **运行时自观测与恢复**：暴露 build、deployment、health、已选资产、capacity、probation 和 rollback
   身份，但不发展成通用运维平台。
5. **能力与边界自模型**：基于 evidence-derived capability profile、约束、不确定性和 Decision Owner
   边界，判断应自行执行、委派、反思还是停止。这是工具调用之上的判断，不是另一个 task router。
6. **资产身份与节点投影**：把可复用资产绑定到固定 source、selection lock、兼容性结果、原子 activation
   receipt、probation 和 rollback。它分发不可变配置，绝不分发 runtime state 或原始 memory。

学习、SOP/skill 成长和新增 Tool Protocol 是这些能力的外延，而不是替代品。因此，交付应先建立前四项能力，
再扩大资产类别或增加 workflow surface。Dream Consolidation 仍只是有边界、只产生 proposal 的学习机制，不是
v0.2 控制路径。共享 memory、通用多 Agent scheduler、自动资产晋升和托管控制面继续不在该边界内。

## 目标

- 让自迭代方向通过有边界 proposal 和 evidence 可见；
- 让经过验证的本地学习成果可以被选定节点复用；
- 让每个已接受资产拥有唯一的 Git 身份和版本历史；
- 让消费资产的 Agent 自己判断兼容性、选择、安装和激活；
- 保留节点本地证据、隐私、回滚和故障隔离；
- 支持 skill、prompt、SOP、Agent profile、指令模板、knowledge pack 和跨 Agent 规范，但不把它们当成无类型的文件同步盘；
- 优先复用 Git、可选 GitHub 表面、Evi 现有 project root 发现能力和文件系统投影，不新建同步服务。

## 非目标

- 同步运行时 state、队列、会话、日志或数据库；
- 同步原始 episode memory 或完整对话历史；
- 让所有节点安装完全相同的资产集合；
- 自动把每个本地产生的 skill 推入 LuBan；
- 未经节点本地验证就全局激活某个 LuBan commit；
- 替代项目自己的 `AGENTS.md`、已接受 ADR 或源码文档；
- 把 Obsidian 当作机器同步协议或 source of truth；
- 在 GitHub Projects 已能满足规划需求时自建 Kanban；
- 把 LuBan 变成公开市场或通用包管理器；
- 引入托管式、多用户的 Evi 控制平面。

## 总体架构

```text
Direction Proposal / 已接受 Goal
        |
        v
原生 Harness -> 代码/文档改动 -> commit 证据（可选 PR/GitHub）
        |
        v
Evi 本地观察 -> candidate -> audit -> 由 Evi 控制的 LuBan proposal PR
                                      |
                                      v
                              accepted LuBan commit
                                      |
                    +-----------------+-----------------+
                    v                 v                 v
                本地开发 Agent      canary Agent      生产 Agent
                选择/验证            选择/验证          选择/验证
                激活/观察            激活/观察          激活/观察
                    |                 |                 |
                    +-------- 节点本地 receipt/evidence +
```

图中的任何箭头都不表示共享运行时状态。Git 只分发不可变的资产版本，Agent 负责本地判断和副作用。

## 所有权矩阵

| 资产面 | 唯一 canonical owner | LuBan 的作用 | 节点的作用 |
| --- | --- | --- | --- |
| Evi 代码和内置契约 | Evi 仓库 | 仅引用 | 部署固定 Evi build |
| Skill、prompt、可复用 SOP | LuBan | 保存已接受正文和历史 | 本地选择和投影 |
| Agent profile overlay | LuBan | 保存版本化 profile | 显式验证和激活 |
| Evi 核心身份基线 | Evi 仓库 | 可保存受治理的 overlay candidate | 不得静默替换基线 |
| 仓库根 `AGENTS.md` | 对应项目仓库 | 只保存模板/片段 | 遵循项目作用域和优先级 |
| 项目规范 | 对应项目文档与 ADR | 不复制 source of truth | 从项目仓库加载 |
| 跨 Agent 通用规范 | LuBan | canonical policy asset | 兼容时才应用 |
| 原始 episode memory | 节点本地 state | 禁止进入 | 本地追加、检索、归档 |
| 已接受共享知识 | LuBan knowledge pack | 保存晋升后的摘要 | 作为有边界的只读 context 导入 |
| 密钥、凭据、cookie | 节点本地 auth | 禁止进入 | 本地解析 |
| 队列、心跳、checkpoint | 节点本地 state | 禁止进入 | 本地运行 |
| 激活 receipt | 节点本地 state | 可接收安全的摘要证据 | 记录精确来源和结果 |

同一正文不能同时存在两个可写 canonical owner。项目专属资产继续留在项目仓库，只有已经证明具有跨项目复用价值并经过明确晋升后，才进入 LuBan。

## 资产分类

### 可直接复用

- skill 及其包内资源；
- prompt 正文和 prompt family；
- 可复用 SOP 和 checklist；
- 工具、adapter 使用说明；
- 模板和参考资料包。

节点完成本地验证后，可以从固定 LuBan checkout 直接选择这些资产。

### 受治理的 overlay

- `soul.md` overlay；
- Agent profile；
- 可复用指令片段；
- 权限、隐私和证据规范；
- 共享 semantic knowledge pack。

这些资产需要更严格的兼容性、来源、敏感级别和回滚证据，不能按普通文件覆盖处理。

### 仅节点本地

- 原始 episode 和完整对话；
- working memory 和当前 checkpoint；
- runtime state、队列、锁、cache、日志和 SQLite 文件；
- 模型和 IM 凭据；
- 浏览器 profile、cookie、token 和主机专属 service 文件；
- 包含私有路径或任务临时事实的未验证 candidate。

## 最小资产契约

LuBan 应通过小型机器可读 manifest 描述资产。最终序列化格式由 LuBan Issue 决定，但必须覆盖：

```yaml
id: stable-asset-id
kind: skill | prompt | sop | profile | instruction | knowledge-pack | policy
version: 1
scope: cross-agent | agent | project-template | node-profile
owner: luban
source:
  type: owned | vendor
  upstream: null
  ref: null
compatibility:
  evi: ">=0.2.0 <0.3.0"
  runtimes: []
activation:
  mode: discovery-root | symlink | copy | context-overlay | manual
sensitivity: public-safe | private | restricted
dependencies: []
verification: []
retirement:
  replaced_by: null
```

Manifest 是声明式数据，不能包含可执行安装命令、凭据、隐式全局激活或隐藏同步行为。

资产身份由 `id + kind` 确定，选中版本必须绑定 LuBan commit 和内容 hash。名称冲突必须 fail closed，不能再用修改时间决定同名资产谁覆盖谁。

## 生命周期

### 1. 本地孵化

Evi 继续把本地 SOP draft、skill candidate、已晋升本地 skill、memory candidate、audit 和 outcome telemetry 写入节点本地 state 和 active vault。本地晋升只表示“本节点可用”，不表示“所有节点已接受”。

### 2. 共享晋升提案

只有同时具备以下内容，Evi 才应提出共享资产：

- 明确且有边界的触发条件和 scope；
- 来源和 evidence refs；
- secret 和私有路径检查；
- 兼容性假设；
- verification command 或已观察 outcome；
- rollback 或 retirement 说明；
- 为什么它不应只留在单个项目或节点的理由。

提案目标是 LuBan branch 或 pull request。Evi 控制何时调用这项 `Shared Asset Promotion`
能力；在适用 policy 允许时，可以创建 proposal branch、commit 和 pull request。该操作属于明确的
外部 Git 副作用，必须记录来源节点和证据，但不能复制原始私有运行时 artifact。

### 3. LuBan 接受

LuBan CI 和仓库规则验证目录结构、manifest 字段、重复身份、禁止文件、来源、第三方资产 license 和声明的验证步骤。接受结果是一个 canonical Git commit，不会自动安装或激活任何内容。

人工审核不是运行时强依赖。在仓库策略允许时，Evi 可以完成基于证据的自治审核；同时继续通过 branch protection 和确定性检查阻止未经验证的 accepted branch 直接修改。创建 proposal 不授予 merge 或 acceptance 权限：它们仍是 LuBan 仓库 policy 的 Decision Owner effect，并与每个节点后续 activation 决策分离。

### 4. 节点选择和激活

每个节点 Agent：

1. fetch LuBan，但不修改当前 active projection；
2. 解析明确的 commit 和资产集合；
3. 验证 manifest、内容 hash、依赖、运行时兼容性和本地 policy；
4. stage 不可变 checkout 或 release 目录；
5. 验证发现结果并运行小型 smoke；
6. 原子切换 `current` 指针或 runtime projection；
7. 记录 activation receipt 和 probation 结果；
8. 保留 `previous` 用于回滚。

不同 Agent 可以选择不同 profile 和资产集合。生产节点通常只使用 LuBan read-only 凭据，不能直接写 accepted branch。

### 5. 效果、修订和退役

使用结果先作为节点本地证据。安全且有价值时，Evi 可以把有边界的 outcome summary 提交回 LuBan proposal 或 GitHub Issue。连续验证成功可以增强推荐，连续 attention、drift 或 failure 可以提出修订或退役。任何 telemetry event 都不能自行重写 accepted asset。

## Memory 模型

v0.2 把记忆分成三类：

1. **Episodic memory**：原始事件和 session evidence，始终保留在节点本地。
2. **Semantic memory**：已接受的长期事实和偏好，默认保留在节点本地。
3. **Shared knowledge pack**：经过明确晋升、限定 scope、脱敏后的 semantic summary，存入 LuBan。

Knowledge pack 必须声明 scope、source refs、confidence、sensitivity、freshness 或 review time、contradiction 和 retirement 条件。导入动作只是只读 context selection，不是合并不同节点的 MemoryStore 数据库。

Obsidian 可以把 LuBan 本地 checkout 作为可选的人类 Markdown 编辑器和导航器，但它的 Sync 不属于 Agent 协议，Obsidian vault 也不能成为第二个 canonical owner。

## 身份和指令文件

Evi 仓库内的核心身份继续作为 baseline。LuBan 中类似 `soul.md` 的资产属于受治理的 profile overlay 或 candidate，不能无条件替换 baseline。涉及身份、权限、隐私、安全或长期决策策略的变化，必须进入 Evi 最高治理等级，并记录 simulation、verification、rollback 和 monitoring evidence。

仓库根 `AGENTS.md` 的语义依赖文件系统 scope 和指令优先级，因此继续由对应项目仓库维护。LuBan 可以保存带明确目标和合并说明的模板/片段。Agent 可以基于模板提出项目改动，但不能全局覆盖项目指令。

## 初始节点拓扑

第一阶段按角色定义，不把主机资源写死到协议：

| 角色 | 初始节点 | 职责 |
| --- | --- | --- |
| development | 本机 | 产生 candidate、运行完整检查、操作 Git 与可选 GitHub 表面 |
| canary | 通过容量 preflight 时使用 SST | 只读消费 LuBan、执行有边界的激活 smoke |
| production | SSR | 运行常驻 Evi service 和生产 probation |

任何 slice 超出 SST 容量时，都可以不使用 SST。跳过不适合的 canary，比假设它与开发机或生产节点等价更安全。

### SSR 部署修正

当前 SSR 部署没有遵守预期的不可变 `next/current/previous` 常驻部署契约，也无法稳定暴露 build identity。v0.2 必须把直接从源码树运行迁移为：

- 固定 commit 的已构建 release directory；
- 位于可替换 release 之外的稳定 supervisor；
- readiness 同时绑定 Evi commit、LuBan commit、selected profile 和 asset lock；
- 接受前执行 probation；
- 自动或人工切回 `previous`；
- 保存节点本地 deployment/activation receipt；
- 两个仓库都不保存 secret。

这是一项部署契约迁移，不是一行进程命令补丁。

## 方向和证据可视化

采用 GitHub Projects 时，它是外部规划和 Kanban 界面；Evi Web Console 继续作为运行时和证据检查界面。v0.2 不在 Evi 内重复实现 Issue 规划系统。

最小证据链为：

```text
Direction Proposal
  -> 已接受 Goal / 原生 Harness evidence
  -> implementation commit 和 checks（可选 PR/GitHub）
  -> 发生资产变化时由 Evi 控制的 LuBan proposal / accepted commit
  -> node activation receipt
  -> runtime verification/outcome evidence
  -> Goal acceptance 或 follow-up
```

每个状态声明都应指向证据链中最新可用的一环。下游证据缺失时，只能把功能描述为已经提案、已经实现或已经部署到实际可证明的阶段。

## 安全和供应链

- LuBan 必须先转为 private，才能写入私有资产或 knowledge pack；
- 开发凭据可以提交 proposal，运行节点通常只配置 read-only deploy key；
- 第三方资产记录 upstream URL、不可变 upstream ref、license、本地修改和内容 hash；
- CI 拒绝 secret、危险 symlink、path escape、异常大型二进制、重复身份和无效 manifest；
- 激活必须固定 commit，不能让 live symlink 指向 mutable branch checkout；
- probation 通过前，节点必须保留上一套 verified asset；
- LuBan 不保存原始 memory、auth、browser state、service state 或 host inventory。

## 交付阶段

### Stage 0：治理和文档

- 记录已接受的 v0.2 决策；
- 区分 v0.1 已实现事实和 v0.2 目标事实；
- 创建 Evi 和 LuBan umbrella Issue；
- 使用 GitHub Projects 展示状态。

### Stage 0.5：core runtime 就绪

- 在扩大资产类别或 workflow surface 前，证明或补齐 Goal 连续性、权威 context 编译、
  outcome-unknown 恢复和 runtime/deployment identity 的有边界缺口；
- 让消费节点可以独立检查当前 Goal、selected context、active asset lock、health 和 recovery state；
- 原生 Harness 继续是唯一的 completion 和 effect-evidence owner。

这是能力基线，不是第二个控制面、工具目录或中心化 state service。它继承已验证的 v0.1 事实，只补齐
会阻止节点成为可持续 v0.2 节点的缺口。

### Stage 1：LuBan registry contract

- 通过明确的仓库管理操作将 LuBan 改为 private；
- 把 catalog 从 skill/prompt 治理扩展为 typed asset；
- 定义 profile、SOP、instruction、knowledge pack 和 policy 布局；
- 增加确定性的 doctor/CI gate 和 branch rule；
- 移除“每次 promotion/install 必须人工批准”的旧假设，同时保留 evidence 和 external-effect gate。

### Stage 2：Evi 只读消费

- 把固定 LuBan checkout 配置为 read-only project root；
- 增加 typed asset discovery，但不改变 local active vault owner；
- 用明确身份和 fail-closed 冲突行为替代按时间戳覆盖；
- 增加兼容性诊断和 asset selection lock。

### Stage 3：Evi proposal flow

- 导出脱敏 candidate，不携带原始运行时 evidence；
- 创建包含 manifest、evidence summary 和 verification 的 LuBan branch/PR；
- 把 accepted/rejected 结果关联回本地治理历史。

### Stage 4：节点事务性激活

- 实现 pinned checkout、staging、verification、atomic activation、probation、receipt 和 rollback；
- 优先修正 SSR 部署，只在容量适合时使用 SST；
- 通过 service health 和 Web Console 暴露 asset/deployment identity。

### Stage 5：共享 knowledge pack

- 定义脱敏、scope、freshness、contradiction 和 retirement 规则；
- 只晋升选中的 semantic knowledge；
- 验证有边界的只读 context 导入；
- MemoryStore 和原始 episode 继续节点本地化。

## 原生交付规则

每个 capability slice 从一个有边界 Goal 和具名 Decision Owner 开始。跨仓库工作保持独立
commit、check、acceptance evidence 与 effect boundary；外部协作确有需要时才使用关联 Issue。

建议顺序：

1. 文档一致性和状态词汇；
2. core continuity、context、harness-recovery 和 runtime-identity 缺口评估与补齐；
3. LuBan private 前置条件和 typed asset schema；
4. Evi 只读 LuBan source 和确定性冲突处理；
5. asset selection lock 和 activation receipt；
6. candidate export 和 LuBan proposal flow；
7. SSR immutable deployment migration；
8. 可选 SST canary activation；
9. knowledge pack promotion/import；
10. Web/service evidence visibility；
11. 端到端多节点 acceptance drill。

每个 slice 在实施前必须写清 owner repo、Goal scope、acceptance、non-goals、verification、external effects、rollback 或 retirement 以及 evidence refs。实质歧义先生成有边界的 `Direction Proposal`；它不是行动授权。

## v0.2 验收条件

只有全部证明，v0.2 才算完成：

- 本地 Evi candidate 能在不携带原始私有 state 的前提下向 LuBan 提案；
- LuBan 能确定性接受或拒绝资产；
- 两个节点解析同一个 accepted LuBan commit，同时独立选择 profile；
- 不兼容或同名冲突资产 fail closed；
- 一个节点激活新资产集，并记录 Evi/LuBan/profile identity；
- probation 失败后恢复上一套资产；
- LuBan 中不存在原始 episodic memory；
- 一个 promoted knowledge pack 以有边界的只读 context 被导入；
- SSR service health 显示已部署 Evi build 和 selected LuBan commit；
- Direction Proposal 或已接受 Goal 可以追踪到 commit、activation 和 verification evidence。
- 一个有边界的 Goal 可以跨 session 或进程边界恢复，其 Decision Owner、selected context 和 outcome
  status 仍然可检查。
- outcome-unknown、failed 和 successful effect 在 recovery 中保持区分；模型 claim 不能单独提供
  completion evidence。

## 回滚边界

架构可以在不删除证据的前提下关闭：

- 移除或禁用 LuBan project root；
- 恢复上一版 local asset-selection lock；
- 把 `current` 切回 `previous`；
- 保持 local active vault 和 MemoryStore 不变；

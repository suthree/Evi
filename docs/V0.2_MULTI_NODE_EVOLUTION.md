# v0.2 Multi-Node Evolution

> Historical Archive / rollback evidence. Captured as the v0.2 direction on
> its original date and retained without rewriting its body. ADR 0018/v0.3 is
> the current architecture and planning baseline; this document is not a
> current roadmap, runtime claim, or default task route.

Historical status: approved v0.2 target architecture; not an implemented runtime contract.

This historical document defined the v0.2 direction for evolving one self-growing agent
across a local development machine and remote runtime nodes. It preserves the
v0.1 evidence, harness, and node-local safety model while adding a private,
Git-backed distribution path for reusable agent assets.

The Simplified Chinese companion is
[`docs/V0.2_MULTI_NODE_EVOLUTION.cn.md`](V0.2_MULTI_NODE_EVOLUTION.cn.md).

## Executive Decision

v0.2 uses three separate planes:

1. Evi's native control plane (`GoalRuntime`, `Harness`, canonical evidence,
   `OutcomeReceipt`, and bounded `Direction Proposal`) owns local direction,
   verification, and self-evolution effects.
2. A private LuBan repository stores accepted, reusable agent assets and their
   version history.
3. Evi evaluates, proposes, selects, validates, activates, observes, revises,
   and retires assets on each node.

GitHub Issues and Projects may expose external planning, status, or delivery
evidence, but they are not a required control plane.

LuBan is an agent asset registry and release source. It is not a runtime
orchestrator, installer daemon, shared state database, or decision engine.
`skill-manager` is a reference implementation for sync, conflict, backup, and
recovery techniques; it is not a v0.2 dependency or standard.

## Core Runtime Boundary

v0.2 does not define progress as a larger collection of tools, skills, or
learned procedures. Its core target is one durable agent runtime that can keep
its identity and make its work inspectable across sessions, restarts, and
independently selected nodes. The required core capabilities are:

1. **Goal continuity**: bind intent, Decision Owner, checkpoints, acceptance,
   and an `OutcomeReceipt` so a Goal survives a session or process boundary.
2. **Context compilation**: select bounded, authoritative goal, project,
   runtime, and recall context; conflicts and stale evidence do not become an
   implicit transcript dump.
3. **Evidence-directed self-supervision**: record actions and effects, classify
   success, failure, and outcome-unknown separately, and recover or pause
   without treating model confidence as verification.
4. **Runtime self-observation and recovery**: expose build, deployment,
   health, selected assets, capacity, probation, and rollback identity without
   making a generic operations platform.
5. **Capability and boundary self-model**: use evidence-derived capability
   profiles, constraints, uncertainty, and Decision Owner boundaries to choose
   whether to act, delegate, reflect, or stop. This is the judgment above a
   tool call, not another task router.
6. **Asset identity and node projection**: bind reusable assets to a pinned
   source, selection lock, compatibility result, atomic activation receipt,
   probation, and rollback. This distributes immutable configuration, never
   runtime state or raw memory.

Learning, SOP/skill growth, and new Tool Protocols extend these capabilities;
they do not replace them. Delivery therefore establishes the first four
capabilities before expanding asset classes or adding workflow surfaces. Dream
Consolidation remains a bounded proposal-only learning mechanism, not a v0.2
control path. Shared memory, a generic multi-agent scheduler, automatic asset
promotion, and a hosted control plane remain outside this boundary.

## Goals

- keep self-evolution direction visible through bounded proposals and evidence;
- let verified local learning become reusable across selected nodes;
- give every accepted asset one canonical Git identity and history;
- keep selection, compatibility judgment, installation, and activation under
  the consuming agent's control;
- preserve node-local evidence, privacy, rollback, and failure isolation;
- support skills, prompts, SOPs, agent profiles, instruction templates,
  knowledge packs, and cross-agent policies without treating them as one
  untyped file dump;
- reuse Git, optional GitHub surfaces, Evi's existing project-root discovery,
  and normal filesystem projections before building another service.

## Non-Goals

- synchronizing raw runtime state, queues, sessions, logs, or databases;
- synchronizing raw episode memory or complete conversation histories;
- making all nodes install the same asset set;
- automatically pushing every locally generated skill into LuBan;
- globally activating a LuBan commit without node-local validation;
- replacing project-owned `AGENTS.md`, accepted ADRs, or source documentation;
- using Obsidian as a machine synchronization protocol or source of truth;
- building a custom Kanban when GitHub Projects covers the planning surface;
- making LuBan a public marketplace or general package manager;
- introducing a hosted multi-user Evi control plane.

## Architecture

```text
Direction Proposal / accepted Goal
        |
        v
native Harness -> code/docs change -> commit evidence (optional PR/GitHub)
        |
        v
Evi local observation -> candidate -> audit -> Evi-controlled LuBan proposal PR
                                             |
                                             v
                                    accepted LuBan commit
                                             |
                       +---------------------+--------------------+
                       v                     v                    v
                 local-dev agent       canary agent       production agent
                 select/validate       select/validate    select/validate
                 activate/observe      activate/observe   activate/observe
                       |                     |                    |
                       +---------- node-local receipts/evidence -+
```

No arrow represents shared runtime state. Git distributes immutable asset
versions; agents own local decisions and effects.

## Ownership Matrix

| Surface | Canonical owner | LuBan role | Node role |
| --- | --- | --- | --- |
| Evi code and built-in contracts | Evi repository | reference only | deploy pinned Evi build |
| Skills, prompts, reusable SOPs | LuBan | canonical accepted body and history | select and project locally |
| Agent profile overlays | LuBan | versioned reusable profile | validate and activate explicitly |
| Core Evi identity baseline | Evi repository | may store governed overlay candidates | never silently replace the baseline |
| Repo-root `AGENTS.md` | owning project repository | templates/fragments only | obey project scope and precedence |
| Project specifications | owning project docs and ADRs | no duplicate source | load from project repository |
| Cross-agent policies | LuBan | canonical policy asset | apply only when compatible |
| Raw episode memory | node-local state | forbidden | append, search, archive locally |
| Accepted shared knowledge | LuBan knowledge pack | canonical promoted summary | import as bounded read-only context |
| Secrets, credentials, cookies | node-local auth | forbidden | resolve locally |
| Queues, heartbeats, checkpoints | node-local state | forbidden | operate locally |
| Activation receipt | node-local state | optional bounded evidence summary | record exact source and result |

The same body must not have two writable canonical owners. A project-specific
asset remains in its project until it has proven cross-project reuse value and
is deliberately promoted into LuBan.

## Asset Classes

### Directly reusable

- skills and their package resources;
- prompt bodies and prompt families;
- reusable SOPs and checklists;
- tool and adapter guidance;
- templates and reference bundles.

These assets may be selected directly from a pinned LuBan checkout after local
validation.

### Governed overlays

- `soul.md` overlays;
- agent profiles;
- reusable instruction fragments;
- permission, privacy, and evidence policies;
- shared semantic knowledge packs.

These assets require stronger compatibility, provenance, sensitivity, and
rollback evidence. They must not be treated as ordinary copy-over files.

### Node-local only

- raw episodes and conversations;
- working memory and current checkpoints;
- runtime state, queues, locks, caches, logs, and SQLite files;
- model and IM credentials;
- browser profiles, cookies, tokens, and host-specific service files;
- unverified candidates containing private paths or task-specific facts.

## Minimal Asset Contract

LuBan should describe assets with a small machine-readable manifest. The exact
serialization belongs to the LuBan issue, but the contract must cover:

```yaml
id: stable-asset-id
kind: skill | prompt | sop | profile | instruction | knowledge-pack | policy
version: 1
scope: cross-agent | agent | project-template | node-profile
owner: luban
source:
  type: owned | vendor
  upstream: null
  ref: null
compatibility:
  evi: ">=0.2.0 <0.3.0"
  runtimes: []
activation:
  mode: discovery-root | symlink | copy | context-overlay | manual
sensitivity: public-safe | private | restricted
dependencies: []
verification: []
retirement:
  replaced_by: null
```

The manifest is declarative. It must not contain executable install commands,
credentials, implicit global activation, or hidden synchronization behavior.

An asset identity is `id + kind`; a selected version is bound to a LuBan commit
and content hash. Name collisions must fail closed. Modification time must not
decide which same-name asset wins.

## Lifecycle

### 1. Local incubation

Evi continues to write local SOP drafts, skill candidates, promoted local
skills, memory candidates, audits, and outcome telemetry to node-local state
and the local active vault. Local promotion means "usable on this node"; it
does not mean "accepted for all nodes."

### 2. Shared promotion proposal

Evi may propose a reusable artifact only after it has:

- a bounded trigger and scope;
- source and evidence references;
- secret and private-path inspection;
- compatibility assumptions;
- verification commands or observed outcomes;
- rollback or retirement guidance;
- a reason it belongs outside one project or node.

The proposal targets a LuBan branch or pull request. Evi controls when this
`Shared Asset Promotion` capability is invoked and may create the proposal
branch, commit, and pull request when the applicable policy allows it. The
proposal operation is an explicit external Git effect and must record the
source node and evidence without copying raw private runtime artifacts.

### 3. LuBan acceptance

LuBan CI and repository rules validate structure, manifest fields, duplicate
identity, forbidden files, provenance, license information for vendor assets,
and declared verification. Acceptance creates a canonical Git commit. It does
not install or activate anything.

Human review is not a mandatory runtime dependency. Evi may complete an
autonomous evidence-backed review when repository policy allows it, while
branch protection and deterministic checks still prevent unvalidated direct
mutation of the accepted branch. Creating a proposal does not grant merge or
acceptance authority: those remain a LuBan repository-policy Decision Owner
effect, separate from each node's later activation decision.

### 4. Node selection and activation

Each node agent:

1. fetches LuBan without mutating the active projection;
2. resolves an explicit commit and asset set;
3. validates manifest, content hash, dependencies, runtime compatibility, and
   local policy;
4. stages an immutable checkout or release directory;
5. verifies discovery and a bounded smoke test;
6. atomically switches a `current` pointer or runtime projection;
7. records an activation receipt and probation result;
8. retains `previous` for rollback.

Agents may select different profiles and asset sets. Production nodes should
normally use read-only LuBan credentials and must not write directly to the
accepted branch.

### 5. Outcome, revision, and retirement

Usage results remain node-local evidence. Evi may publish a bounded outcome
summary back to a LuBan proposal or GitHub issue when it is useful and safe.
Repeated verified success can strengthen a recommendation. Repeated attention,
drift, or failure can propose revision or retirement. No telemetry event may
rewrite an accepted asset by itself.

## Memory Model

v0.2 separates three memory classes:

1. **Episodic memory**: raw events and session evidence; always node-local.
2. **Semantic memory**: accepted durable facts and preferences; node-local by
   default.
3. **Shared knowledge packs**: deliberately promoted, scoped, redacted semantic
   summaries stored in LuBan.

A knowledge pack must declare scope, source refs, confidence, sensitivity,
freshness or review time, contradictions, and retirement conditions. Import is
read-only context selection, not a merge of MemoryStore databases.

Obsidian may open a local LuBan checkout as an optional human Markdown editor
and navigator. Its sync feature is not part of the agent protocol, and an
Obsidian vault must not become a second canonical owner.

## Identity And Instruction Files

Evi's repository-owned core identity remains the baseline. A LuBan
`soul.md`-style asset is a governed profile overlay or candidate, not an
unconditional replacement. Any identity, permissions, privacy, safety, or
long-term decision-policy change uses Evi's highest governance tier and records
simulation, verification, rollback, and monitoring evidence.

Repo-root `AGENTS.md` files remain owned by their repositories because their
meaning depends on filesystem scope and instruction precedence. LuBan may store
reusable templates and fragments with explicit target and merge guidance. An
agent may propose a project change from such a template, but must not globally
overwrite project instructions.

## Initial Node Topology

The first rollout uses roles rather than hard-coding host capabilities:

| Role | Initial node | Responsibility |
| --- | --- | --- |
| development | local machine | author candidates, run full checks, operate Git and optional GitHub surfaces |
| canary | SST when capacity preflight passes | read-only LuBan consumption and bounded activation smoke |
| production | SSR | resident Evi service and production probation |

SST is optional for any slice that exceeds its capacity. Skipping an unsuitable
canary is safer than pretending the node is equivalent to the development or
production node.

### SSR deployment correction

The current SSR deployment does not follow the intended immutable
`next/current/previous` resident deployment contract and does not reliably
expose build identity. v0.2 must replace direct source-tree execution with:

- a pinned, built release directory;
- a stable supervisor outside the replaceable release;
- readiness tied to Evi commit, LuBan commit, selected profile, and asset lock;
- probation before acceptance;
- automatic or operator-invoked rollback to `previous`;
- node-local deployment and activation receipts;
- no secrets inside either repository.

This correction is a deployment-contract migration, not a one-line process
patch.

## Direction And Evidence Visibility

When adopted, GitHub Projects is an external planning and Kanban surface. Evi's
web console remains a runtime and evidence inspection surface. v0.2 does not
duplicate issue planning inside Evi.

The minimum evidence chain is:

```text
Direction Proposal
  -> accepted Goal / native Harness evidence
  -> implementation commit and checks (optional PR/GitHub)
  -> Evi-controlled LuBan proposal / accepted commit when assets change
  -> node activation receipt
  -> runtime verification/outcome evidence
  -> Goal acceptance or follow-up
```

Every status claim should point to the latest available link in that chain.
Missing downstream evidence means the feature is proposed, implemented, or
deployed only up to the proven stage.

## Security And Supply Chain

- LuBan must become private before private assets or knowledge packs enter it.
- Development credentials may propose changes; runtime nodes normally receive
  read-only deploy keys.
- Vendor assets record upstream URL, immutable upstream ref, license, local
  modifications, and content hash.
- CI rejects secrets, unsafe symlinks, path escape, oversized unexpected
  binaries, duplicate identities, and invalid manifests.
- Activation uses a pinned commit, never a mutable branch checkout behind a
  live symlink.
- A node must retain the previous verified asset set until probation passes.
- LuBan contains no raw memory, auth, browser state, service state, or host
  inventory.

## Delivery Stages

### Stage 0: governance and documentation

- record the accepted v0.2 decision;
- keep v0.1 implemented facts distinct from v0.2 target facts;
- create Evi and LuBan umbrella issues;
- make GitHub Projects the visible status surface.

### Stage 0.5: core runtime readiness

- demonstrate or close the bounded gaps in Goal continuity, authoritative
  context compilation, outcome-unknown recovery, and runtime/deployment
  identity before expanding asset classes or workflow surfaces;
- make the current Goal, selected context, active asset lock, health, and
  recovery state independently inspectable on the consuming node;
- retain the native Harness as the only completion and effect-evidence owner.

This is a capability baseline, not a second control plane, tool catalog, or
central state service. It carries forward verified v0.1 facts and closes only
the gaps that block a durable v0.2 node.

### Stage 1: LuBan registry contract

- make LuBan private through an explicit repository administration action;
- generalize the catalog from skill/prompt-only governance to typed assets;
- define layouts for profiles, SOPs, instructions, knowledge packs, and
  policies;
- add deterministic doctor/CI gates and branch rules;
- remove assumptions that every promotion or install is human-gated while
  retaining evidence and external-effect gates.

### Stage 2: read-only Evi consumption

- configure a pinned LuBan checkout as a read-only project root;
- add typed asset discovery without changing the local active-vault owner;
- replace timestamp collision resolution with explicit identity and fail-closed
  conflict behavior;
- add compatibility diagnostics and an asset selection lock.

### Stage 3: Evi proposal flow

- export sanitized candidates without raw runtime evidence;
- create a LuBan branch/PR with manifest, evidence summary, and verification;
- reconcile accepted/rejected proposals back into local governance history.

### Stage 4: transactional node activation

- implement pinned checkout, staging, verification, atomic activation,
  probation, receipt, and rollback;
- correct SSR deployment first, then use SST only where its capacity is
  suitable;
- expose asset/deployment identity through service health and the web console.

### Stage 5: shared knowledge packs

- define redaction, scope, freshness, contradiction, and retirement rules;
- promote selected semantic knowledge only;
- validate bounded read-only import into context;
- keep MemoryStore and raw episodes node-local.

## Native Delivery Rules

Each capability slice starts from one bounded Goal and named Decision Owner.
Cross-repository work keeps separate commits, checks, acceptance evidence, and
effect boundaries; linked issues are optional when external coordination needs
them.

Recommended task order:

1. documentation consistency and status vocabulary;
2. core continuity, context, harness-recovery, and runtime-identity gap
   assessment and closure;
3. LuBan privacy prerequisite and typed asset schema;
4. Evi read-only LuBan source and deterministic collision handling;
5. asset selection lock and activation receipt;
6. candidate export and LuBan proposal flow;
7. SSR immutable deployment migration;
8. optional SST canary activation;
9. shared knowledge-pack promotion and import;
10. web/service evidence visibility;
11. end-to-end multi-node acceptance drill.

Each slice must state owner repo, Goal scope, acceptance, non-goals,
verification, external effects, rollback or retirement, and evidence refs
before implementation begins. Material ambiguity first produces a bounded
`Direction Proposal`; it is not authority to act.

## v0.2 Acceptance

v0.2 is not complete until all of these are demonstrated:

- a local Evi candidate is proposed to LuBan without raw private state;
- LuBan deterministically accepts or rejects the asset;
- two nodes resolve the same accepted LuBan commit while selecting profiles
  independently;
- an incompatible or colliding asset fails closed;
- one node activates a new asset set and records Evi/LuBan/profile identities;
- a failed probation restores the previous asset set;
- raw episodic memory remains absent from LuBan;
- one promoted knowledge pack is imported as bounded read-only context;
- SSR service health reports the deployed Evi build and selected LuBan commit;
- a Direction Proposal or accepted Goal can be traced through commits,
  activation, and verification evidence.
- a bounded Goal can resume across a session or process boundary with its
  Decision Owner, selected context, and outcome status still inspectable.
- outcome-unknown, failed, and successful effects remain distinct through
  recovery; no model claim alone supplies completion evidence.

## Rollback Boundary

The architecture can be disabled without deleting evidence:

- remove or disable the LuBan project root;
- restore the previous local asset-selection lock;
- switch `current` back to `previous`;
- keep the local active vault and MemoryStore unchanged;
- mark the failed LuBan asset version retired or incompatible;
- preserve proposal, activation, and failure evidence for follow-up.

No rollback rewrites Git history, erases node-local episodes, or silently
reactivates a mutable branch.

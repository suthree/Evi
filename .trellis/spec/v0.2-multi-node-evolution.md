# v0.2 Multi-Node Evolution

Status: approved target specification. No item in this document is implemented
merely because it is specified here.

## Purpose

Extend the released v0.1 local runtime into a federated, single-user,
multi-node evolution model. Each node keeps execution and runtime state local.
A private LuBan Git repository distributes accepted reusable assets. Evi is the
first and primary agent that evaluates, proposes, consumes, activates, observes,
revises, and retires those assets.

The stable design and operator-facing explanation live in
`docs/V0.2_MULTI_NODE_EVOLUTION.md` and its `.cn.md` companion. This file owns
the implementation boundary that future Trellis tasks must preserve.

## Required Planes

1. GitHub Issues/Projects own public-safe direction, status, and cross-repo
   delivery evidence.
2. Trellis owns bounded implementation tasks inside each repository.
3. LuBan owns accepted reusable asset bodies, typed metadata, provenance, and
   Git history.
4. Evi owns agent judgment, local-learning promotion, shared-promotion
   proposals, compatibility decisions, local activation, outcome evidence, and
   rollback decisions.
5. Each node owns raw memory, runtime state, secrets, queues, working
   checkpoints, active projections, and activation receipts.

Trellis, LuBan, and Evi must not absorb one another's owner surfaces.

## Required Asset Boundary

LuBan may own accepted:

- skills;
- prompts;
- reusable SOPs;
- agent profile overlays;
- reusable instruction templates and fragments;
- cross-agent policies;
- redacted, scoped semantic knowledge packs;
- tool and adapter guidance.

LuBan must reject:

- raw episodes or conversations;
- working memory and volatile task state;
- credentials, cookies, browser profiles, or auth files;
- service state, queues, locks, logs, databases, or host inventories;
- project-owned `AGENTS.md` files presented as global replacements;
- project-specific specs presented as cross-agent truth;
- mutable-branch identities for activated assets.

## Required Identity And Version Contract

- Asset identity is explicit and typed; same-name resolution must not use
  modification time.
- A selected version binds an asset ID, kind, LuBan commit, and content hash.
- Duplicate or ambiguous identities fail closed and provide bounded operator
  guidance.
- Manifests declare scope, source, compatibility, activation mode,
  sensitivity, dependencies, verification, and retirement metadata.
- Vendor assets declare immutable upstream refs, license, and local
  modifications.
- Manifests remain declarative and contain no credentials or executable install
  side effects.

## Required Learning And Promotion Contract

- The node-local active vault remains the local learning write target.
- Local promotion means the asset is usable on that node only.
- Shared promotion is a separate external Git proposal to LuBan.
- A proposal contains a sanitized body, typed manifest, evidence summary,
  compatibility assumptions, verification, and rollback or retirement notes.
- Proposals must not copy raw runtime evidence or private host paths.
- LuBan acceptance records a canonical commit but performs no installation.
- Rejection, acceptance, revision, and retirement link back to node-local
  governance history without rewriting it.

## Required Consumption And Activation Contract

Every node agent must independently:

1. fetch without touching the active projection;
2. select an explicit LuBan commit and profile;
3. validate manifest, hash, dependencies, compatibility, and policy;
4. stage an immutable release or checkout;
5. run deterministic discovery and bounded smoke checks;
6. atomically switch the active projection;
7. record Evi commit, LuBan commit, profile, asset lock, result, and evidence;
8. keep the previous verified projection until probation passes;
9. fail closed and roll back when acceptance fails.

Runtime nodes normally use read-only LuBan credentials. No node may run a live
projection through a symlink to a mutable branch checkout.

## Required Memory Contract

- Episode and working memory remain node-local.
- Semantic memory remains node-local by default.
- Only explicitly promoted, scoped, redacted semantic summaries may become
  shared knowledge packs.
- A knowledge pack declares source refs, confidence, sensitivity, freshness or
  review time, contradictions, and retirement conditions.
- Import is bounded read-only context selection, never a database merge.
- Obsidian may be an optional editor over a local checkout; it is not a sync
  protocol or canonical owner.

## Required Identity And Instruction Contract

- Evi's repository-owned core identity remains the baseline.
- LuBan may store governed identity/profile overlays, not silent baseline
  replacements.
- Identity, permission, privacy, safety, or long-term policy changes use the
  highest governance tier with simulation, verification, rollback, and
  monitoring evidence.
- Repo-root instruction files remain owned by their repositories.
- LuBan instruction assets are templates/fragments with target scope and merge
  guidance.

## Required Deployment Contract

- The local machine is the initial development role.
- SSR is the initial production role.
- SST is an optional canary only after capacity and dependency preflight.
- SSR direct source-tree execution is a migration gap, not an accepted
  production pattern.
- Production uses a stable supervisor outside immutable
  `next/current/previous` releases.
- Readiness and receipts bind Evi commit, LuBan commit, selected profile, and
  asset lock.
- Deployment and asset probation must have deterministic rollback.
- Secrets and node state remain outside Evi and LuBan repositories.

## Required Operator Visibility

- GitHub Projects is the Kanban and roadmap view.
- Evi web/service views expose runtime, deployment, selection, and evidence
  state only; they do not duplicate issue planning.
- Status uses explicit stages: proposed, planned, implemented, accepted,
  deployed, verified, blocked, or rolled back.
- The evidence chain is issue -> Trellis task -> PR/commit/checks -> optional
  LuBan proposal/commit -> activation receipt -> runtime verification -> issue
  acceptance.
- A missing downstream link cannot be replaced by a model status claim.

## Branch Authority And Release Gate

Local worktrees and feature branches are autonomous iteration surfaces. Within
an accepted Goal and Trellis task, Evi may create branches, modify files, run
checks, commit, push, open pull requests, and maintain those pull requests
without per-action operator confirmation.

`develop` is the integration branch:

- Evi may merge its own pull request into `develop` without a separate human
  approval when the linked Issue and Trellis task are in scope, required
  verification has passed, the pull request records the evidence, and no known
  blocker remains.
- Changes must enter `develop` through a pull request. Direct pushes, force
  pushes, and branch deletion are not part of the autonomous contract.
- A failed or incomplete check, unresolved blocker, scope drift, or missing
  completion evidence prevents autonomous merge.
- Until repository CI enforces the gate, the pull request must record the local
  targeted checks and `pnpm run check`. Once CI exists, its required checks must
  also pass.

`main` is the release branch and the operator merge gate:

- Evi may prepare a release branch and open a pull request from `develop` to
  `main`, but it must not merge that pull request without an explicit operator
  instruction for the named release.
- Direct pushes, force pushes, deletion, automatic merge, and Agent bypass are
  prohibited.
- `pnpm run release:verify`, real model/IM smoke, resident restart/rollback
  smoke, version scope, and release evidence must be complete before operator
  approval.
- Creating a version tag or GitHub Release remains a separate public-release
  effect and also requires explicit operator authorization.

GitHub rulesets should eventually enforce both layers: pull requests and
no-force/no-delete for `develop`; pull requests, required checks, operator
review, and no bypass for `main`. The absence of a GitHub rule does not broaden
the authority defined here.

## Repository And Task Boundary

Future Trellis work must use one task per repository and bounded capability
slice. Cross-repo work uses linked issues and separate diffs, verification,
commits, and rollback evidence.

Recommended task sequence:

1. Evi documentation status and vocabulary consistency;
2. LuBan private-repository prerequisite and typed asset schema;
3. Evi read-only LuBan source and deterministic conflict handling;
4. asset selection lock and activation receipt;
5. Evi candidate export and LuBan proposal flow;
6. SSR immutable deployment migration;
7. optional SST canary activation;
8. knowledge-pack promotion and read-only import;
9. service-health and web evidence visibility;
10. end-to-end multi-node acceptance drill.

Each task must declare owner repo, linked issue, acceptance, non-goals,
verification, external effects, rollback, and evidence refs before mutation.

## Global Non-Goals

- hosted multi-user control plane;
- shared runtime database or cross-node queue;
- public asset marketplace;
- mandatory `skill-manager` dependency;
- custom Kanban implementation;
- automatic global activation;
- identical asset sets on every node;
- raw memory synchronization;
- compatibility claims for every external agent runtime.

## v0.2 Acceptance Gate

The version gate requires live evidence that:

- Evi proposes one sanitized local asset to LuBan;
- LuBan deterministically accepts or rejects it;
- two nodes resolve the same accepted LuBan commit with independent profiles;
- ambiguous or incompatible assets fail closed;
- one node activates and records a complete identity receipt;
- failed probation restores the previous projection;
- raw episodic memory is absent from LuBan;
- one shared knowledge pack is imported as bounded read-only context;
- SSR health reports Evi and LuBan deployment identities;
- the GitHub issue is traceable through Trellis, commits, activation, and
  verification evidence.

Until this gate passes, v0.2 remains partially delivered and v0.1 current-fact
documents must not claim full multi-node support.
